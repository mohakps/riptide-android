## v0.3.3 addendum (2026-11-08)

The user reported the background fix did not work: the PC stayed
connected while the app was minimised, but showed disconnected the
moment the app was reopened. The foreground service half works (the
socket stays alive while minimised). The break was the return-path
liveness check: verifyAlive sent one ping and waited 3 s for the
pong, and a single slow or lost pong failed the session and closed
the socket. The check now retries once before failing the session.

The rejoin half has a second, PC-side cause, found by reading the
PC v1.3.1 source: HostListener.wait_for_client accepts exactly one
connection and then closes the server socket, the Create screen
worker calls it once and never loops, and SessionScreen
_on_session_error only sets a status and never re-arms the
listener. So after any session ends, nothing listens on port 50000
until the user manually goes back to Create Server. A rejoin dial
gets "Connection refused" until then. Fixing that needs a PC-side
change (loop the listener after a session ends); it is not part of
this Android release.

Verification state: debug build, unit tests and lint run on the
build machine; release APK built, signed and uploaded for the
user's phone. The reopen behaviour itself can only be verified live
on the Nothing Phone (2).

Recent devices showed (ip, ip) on both lines, on the Transfer tab

## v0.2.2 addendum (2026-11-07)

The user reported that minimising the app for more than 5 seconds
broke the connection, which made even the file picker unusable: the
system picker backgrounds the app, and the session was gone before a
file could be picked.

Cause, from reading the code: TransferService only called
`startForeground` while a transfer was active and called `stopSelf`
when idle, so while connected and picking a file no foreground
service ran at all. The PC never closes an idle session (blocking
socket, TCP keepalive, no idle timeout in v1.3.1 source) and the
phone socket has no read timeout, so the break was the process being
reclaimed in the background, not a protocol timeout.

Fixes (versionCode 5): session-lifetime foreground service with a
persistent "Connected to PC" notification, session-lifetime wake
lock, liveness check (ping/pong) on return to the foreground with
automatic rejoin of the last peer, and the same check before a send
or download starts. No battery-setting change is required. Full
details in the README v0.2.2 section.

Verification state: Kotlin compile-checked only. No APK was built
for 0.2.2 at the user's direction (0.3 follows with more changes),
so there is no release APK, no hash, and no live phone test yet.
The new paths (service lifecycle, verifyAlive, auto-rejoin) are NOT
covered by unit tests (SessionManager needs an Android Context).

## v0.2.1 addendum (2026-11-07, after the v0.2 live test)

The user tested v0.2 on the Nothing Phone (2) and liked the UI, but the
send failed again: "send failed: Broken pipe (0 of 382450369 bytes
sent)", shown on Home as "Couldn't reach this PC". Address was
192.168.1.6 (LAN), phone code 598-731.

Diagnosis (all on the build machine, against real PC v1.3.1 code from
mohakps/riptide main 61bbf14):
- A Python phone simulation (same TLS handshake, signed hello
  challenge, same framing, 128 KB chunks) sends 5 MB and 365 MB
  successfully, SHA-256 verified, ack ok=True.
- A threaded simulation (reader thread + heartbeat thread + send lock,
  365 MB throttled to 2 MB/s so PC pings arrive mid-send) also
  succeeds: all 382,730,240 bytes received, SHA-256 matches, ack ok.
  The protocol and the concurrency pattern are exonerated; v1.3 and
  v1.3.1 differ only in identity.py, so this covers the user's v1.3 PC.
- The remaining failure mode is a silently dead socket: the reader
  blocks forever on it, and the heartbeat used to swallow its write
  failure, so nothing marked the session dead until the next send
  wrote to it and got Broken pipe at 0 bytes. The exact event that
  killed the socket in the user's test is still unknown (most likely
  the network dropping during the long spool of a cloud video, or the
  PC sleeping); the user was asked what the PC showed and whether the
  file was local or cloud.

Fixes in v0.2.1 (versionCode 4):
- Heartbeat write failure now marks the session FAILED with
  "Connection lost." and closes the dead socket (within 10 s).
  CancellationException from a deliberate disconnect is excluded.
- sendFile and requestDownload refuse when not CONNECTED instead of
  writing to a dead socket.
- Reader "bye" closes the socket and drops to FAILED; reader "error"
  no longer breaks the reader loop; reader failure closes the socket.
  CancellationException in the reader is no longer reported as a
  failure (clean disconnect left a stale error on Home).
- Transfer errors moved to their own flow; Home shows session errors
  only, Session shows transfer errors. The interrupted card (state 13)
  is now reachable: MainActivity keeps the Session screen up while
  showInterrupted is true.
- Address placeholder is now 203.0.113.10 (documentation range), not
  the user's real DDNS hostname.
- Debug build OK, 34/34 unit tests pass, lint clean. The new reader /
  heartbeat / send-guard paths are NOT covered by unit tests
  (SessionManager needs an Android Context); they were verified by
  the Python reproductions above for the protocol side only.
- Live phone retest of a real send is still the user's step.

## v0.4 addendum (MainThread fix + Session polish, 2026-11-08)

  verifyAlive ran on the main thread and its ping write threw
  NetworkOnMainThreadException instantly on reopen. The catch-all
  treated it as "Connection lost" and failSession closed a healthy
  socket. The socket was healthy while minimised (heartbeat ping and
  reader pong at 02:42:31) and the session was CONNECTED at reopen.
  The reader and heartbeat "Socket closed" lines were consequences,
  not causes. The v0.3.3 retry never ran because the write threw on
  attempt 1. This disproves the earlier "socket dies silently while
  minimised" theory.
- Fix: the ping write in verifyAlive now runs on Dispatchers.IO
  (withContext), so the check can no longer fail a live session this
  way. This also covers the pre-send and pre-download checks, which

  CancellationException instead of failing the session.

## v0.5.1 addendum (launch crash fix, 2026-11-08)

- v0.5 crashed on launch. Root cause: ReceiveFolderRepository
  declared its own `preferencesDataStore(name = "riptide")` alongside
  PeerRepository's. Each delegate creates its own DataStore for the
  same file, and DataStore throws IllegalStateException ("multiple
  DataStores active for the same file") when both are used. The
  SessionManager constructed the ReceiveFolderRepository and called
  load() (creating DataStore 1), then its init coroutine called
  peers.loadPeers() (creating DataStore 2), so the app died during
  startup. The fix is a single shared delegate
  (`data/RiptideDataStore.kt`) that both repositories use. The
  receive folder also no longer loads synchronously during
  SessionManager construction; it starts at the default and loads in
  the background init coroutine.
- Build evidence: compile, 35/35 unit tests, assembleRelease —
  BUILD SUCCESSFUL. Release APK 47 MB, versionCode 13, versionName
  0.5.1, SHA-256
  0e6d5430426493d81816bb047febc83e7b1ecb094938a6433cf91960df6c99d6, same
  signing cert c7b64485 (installs as an update).

## v0.7 addendum (batch send, transfer ETA, Join PC validation, 2026-11-08)

  existing single-file send; two or more are one batch in picker
  result order. sendSingleFile is the awaitable single-file operation
